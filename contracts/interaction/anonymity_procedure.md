| 角色 | 谁承担 | 边界 |

**硬约束：**

1. 匿名化执行与赋值表封存必须由**不参与任何一类判分的一方**承担。B.5.2 允许两类判断由同一人承担，因此该封存方**不得是任一判分人**。
2. 判分人不得自行生成 X/Y 标签、不得自行执行匿名化、不得在提交冻结前以任何方式接触赋值表或其种子／抽签记录；采用 §2.2 方式 B（物理抽签）时，判分人不得在场旁观、不得参与抽签，`在场人` 名单中不得出现任一判分人——在场即在提交冻结前知道来源，正是 B.6.4 `EVAL_BLINDING_BROKEN` 的字面含义「裁判提交前知道来源」（B:927）。违反即落入 §6 第 1 行。
3. 封存方式已由 Founder 2026-08-17 定格为**机制而非人选**：脚本随机 + 密封文件 + git 哈希封存。出处：`acceptance/cases/OPEN_QUESTIONS.md` 文首预裁决⑥「匿名三关键：脚本随机+密封文件+git 哈希封存 / 阶段 D 与终审独立随机 / 揭盲后禁回改（要改=重测）」；登记见《裁决台账》08-17「IA-0 预裁决（8 主题整体按推荐）」行。该机制成立的**准确边界（不夸大、不宣称不可读）**：① 脚本产出不经人眼；② 密封文件**生成即 git 提交**，封存后**不可篡改而不被发现**（揭盲时重算哈希与封存提交比对即可暴露事后调换，见 §2.4）；③ 本仓**未**对密封文件施加加密／口令／承诺值，因此「解封前不可读」**不是**本流程提供的技术保证——本仓已是公开仓库，对文件有读权限者在技术上可读到内容。硬约束 1（封存方非判分人）与硬约束 2（判分人冻结前不得接触赋值表／种子）因此是**纪律性约束 + 事后可核验**，不是技术上的不可能：本文件不配套自动检测器，该两条在无检测器时按 `acceptance/README.md` 纪律记 `PENDING_HUMAN`，**绝不因「机制已定格」就自动判为已满足**（防假绿）。在此边界内，B.5.2 v0.2 修订取消外部制作裁判（B:771）后本流程**不再需要第三方人选**。Gate IA-0「裁判与匿名流程已确定」（B:997）就本项的要求即以本条关闭。

## 2. X／Y 标签随机分配与可复核留档

### 2.1 匿名处理要求（B.2.5 原文照抄，不得改写）

> 端到端结果必须：
>
> - 使用随机 X、Y 标签；
> - 隐藏生成来源；
> - 使用相同外层展示格式；
> - 隐藏系统名、Prompt、调用次数和模型日志；
> - 随机排列展示顺序；
> - 在揭晓来源前冻结裁判原始选择。
>
> 匿名处理不得修改业务内容。

注：「随机 X、Y 标签」（B:223）与「随机排列展示顺序」（B:227）在 B.2.5 中是并列的两条要求，本文件 §2.3 对二者分别留档（同一张赋值记录内的 `label_map` 与 `display_order` 两个字段）。二者必须来自**两次互不相关的随机**：在预裁决⑥已定的脚本随机框架内，由同一记录种子派生两条互不相关的子流，分别产出 `label_map` 与 `display_order`；`seed_or_draw_record` 同时记录种子值与派生方式（算法+版本+脚本路径）。出处：《裁决台账》08-17「修复批次两裁决」行②「P-10 X/Y 标签与展示顺序=两次独立随机（同种子派生互不相关子流）」。

### 2.2 允许的两种分配方式（二选一，留档字段相同）

| 方式 | 做法 | 必须留档的东西 |
|---|---|---|
| A｜可复现随机种子 | 用固定算法 + 记录随机种子生成赋值与展示顺序（预裁决⑥「脚本随机」的标准路径） | 种子值、两条子流的派生方式、算法与版本、执行命令或脚本路径 |

### 2.4 可复核判据（照 B.10 口径，不自造）

> B.10 原文：「blind_label_map 只能在 `choices_frozen_at` 后揭晓，并必须足以证明两类裁判实际选择的是哪一侧。」（B:1123）

判据就是这一条：解封后的赋值记录，配上两类裁判已冻结的选择，必须能确定每一类裁判实际选的是 DIYU 侧还是 BASELINE 侧。§2.2 两种分配方式（A 可复现随机种子 / B 物理抽签）各自按表留档齐备，即视为满足本判据；本文件**不另设 B 没有的附加判据**（例如「由不在场第三方独立重建」——物理抽签是一次性物理事件，天然不可重建，那样写会让方式 B 恒不可通过）。

**防事后调换的证明方式已定格**（预裁决⑥「脚本随机+密封文件+git 哈希封存」）：赋值脚本输出写入密封文件，**生成即 git 提交**，以该提交哈希 + 提交时间为封存凭证；揭盲时重算密封文件哈希并与封存提交比对，**一致方可采信该赋值记录**——比对通过即可证明 X/Y 赋值与展示顺序未被事后调换。采用 §2.2 方式 B 时，抽签结果原件／照片同样须入密封文件走同一封存链。比对不一致（记录齐全但真实性不可证）按 §6 第 5 行处理，标签 `EVAL_BLINDING_PROCEDURE_INVALID`（B v0.4 B.6.4）。

赋值记录缺失、或虽在但不足以读出上述映射 → 按 §6 第 4 行处理，且在补齐前**不得**判该案例 PASS（B.1.1 三层证据缺一不可）。
